LLM Provider 接入方案

Demo 中接入真实 Claude / OpenAI，须择其架构

A

纯前端直连（API Key in browser）

用户在 demo UI 输入 API Key，前端直接调用 Claude/OpenAI API。无需后端。Key 仅存 localStorage，不落盘。

Pros

  • 零部署，纯静态 demo
  • 实现最简，仅需 fetch + SSE 解析
  • 与现有 mock provider 同构

Cons

  • API Key 暴露于浏览器（demo 场景可接受）
  • CORS：OpenAI 允许浏览器直连，Claude API 需 proxy 或 CORS header
B

轻量 proxy（Vite dev server middleware）

Vite dev server 加一层 proxy middleware，前端 POST /api/chat → proxy 转发至 Claude/OpenAI。API Key 存 .env，不进浏览器。

Pros

  • Key 不暴露于前端
  • 无 CORS 问题，统一 proxy
  • 可同时支持 Claude + OpenAI

Cons

  • 仅 dev 模式可用，非纯静态
  • 需写 proxy middleware（约 100 行）
C

混合方案（前端直连 + 可选 proxy）

默认前端直连（用户填 Key），同时提供 Vite proxy 路径。UI 中可切换 provider 来源。适合不同测试场景。

Pros

  • 灵活，覆盖两种场景
  • Claude 走 proxy（解决 CORS），OpenAI 可直连

Cons

  • 实现略复杂
